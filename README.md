# 胶片档案扫描整理 API

面向胶片档案扫描整理的本地 API：按批提交胶卷编号、预期帧号起止范围与扫描帧号列表，
服务自动完成**跨批次帧号合并、重复帧识别（只计一次并单独列出）、预期范围内连续缺帧区间计算**。
批次导入**幂等**——重复导入相同批次不会改变任何结果；误导入的批次可按 `batch_id` **撤销**，
撤销后按剩余批次原导入顺序自动重建范围、帧归属与各批明细。
此外支持**补扫任务认领**：把缺帧区间原子切分给不同领取人，任务有有效期，
到期自动让出帧段，并发领取绝不交叠；补扫完成后凭认领提交**完成回执**，
实际扫到的帧以扫描批次入库、认领在同一事务内结案，部分补扫后剩余缺帧立即重新可领。
还可对胶卷拍摄**交付快照**：一致性读中固化当时的预期覆盖、实扫帧与缺帧闭区间，
之后随时按区间集合运算查询当前相对快照三个维度的新增/消失差异；
快照一经生成不随批次导入、撤销或补扫改变，胶卷最后一批被撤销后仍可对比（按空状态）。
并提供**胶卷帧号扫描溯源**：按实际存在的帧号升序分页追查每帧由哪些批次扫描，
给出首扫批次、各参与批次（原导入顺序）及原始列表中的出现次数，
撤销批次后实时重算、首扫归属随之转移。

技术栈：Python + FastAPI + SQLite（单文件库，零外部依赖）。

## 一条命令启动

```bash
docker compose up -d --build
```

启动后访问：

| 用途 | 地址 |
| --- | --- |
| API 服务（端口 **8000**） | http://localhost:8000 |
| 健康检查 | http://localhost:8000/health |
| Swagger 交互文档 | http://localhost:8000/docs |
| OpenAPI 描述 | http://localhost:8000/openapi.json |

停止 / 查看日志：

```bash
docker compose down        # 停止（数据保留在 volume 中）
docker compose logs -f     # 查看日志
```

## 配置（环境变量）

均为可选项，默认值开箱即用：

| 变量 | 默认值 | 说明 |
| --- | --- | --- |
| `PORT` | `8000` | 服务监听端口（改端口时 compose 的 `ports` 也要同步调整） |
| `HOST` | `0.0.0.0` | 监听地址 |
| `DB_PATH` | `/data/film.db` | SQLite 数据库文件路径，启动时自动建库建表 |
| `DB_TIMEOUT` | `30000` | SQLite 写锁等待毫秒数 |

数据持久化在 compose 命名卷 `film-data`（容器内 `/data`）。
改用宿主机目录持久化可把 compose 中的 `film-data:/data` 换成 `./data:/data`。

## API 一览

### 1. 提交扫描批次（幂等）

```bash
curl -X POST http://localhost:8000/batches \
  -H 'Content-Type: application/json' \
  -d '{
    "roll_no": "R-001",
    "expected_start": 1,
    "expected_end": 12,
    "frames": [1, 2, 2, 3, 5, 8, 9, 10, 12],
    "batch_id": "b-2026-001"
  }'
```

字段说明：

- `roll_no`：胶卷编号（必填）
- `expected_start` / `expected_end`：本批预期帧号起止（闭区间，整数 ≥ 0，end ≥ start）
- `frames`：本批扫描帧号列表（至少 1 个；批内重复会被识别为重复帧）
- `batch_id`：可选；提供后可用它查询批次。留空则服务端自动生成

响应（首次导入 `201 Created`）：

```json
{
  "batch_id": "b-2026-001",
  "roll_no": "R-001",
  "repeated": false,
  "added_frames": [1, 2, 3, 5, 8, 9, 10, 12],
  "duplicates": [2],
  "merged_frames": [1, 2, 3, 5, 8, 9, 10, 12],
  "expected_ranges": [[1, 12]],
  "missing_ranges": [[4, 4], [6, 7], [11, 11]],
  "out_of_range_frames": [],
  "created_at": "2026-09-23T06:00:00.000Z"
}
```

**幂等行为**：同一胶卷下，用相同的预期范围 + 相同帧号集合再次提交（无论是否带相同
`batch_id`），返回 `200 OK` 且 `"repeated": true`，不写入任何数据，胶卷汇总结果不变。

跨批次合并示例（继续上面的胶卷提交第二批 `[11, 12, 12, 13]`，预期范围 `10-14`）：

- `added_frames = [11, 13]`（12 已由上一批扫到）
- `duplicates = [12]`（12 跨批次重复；批内重复的 12 同样只计一次）
- `merged_frames` 为该胶卷全部帧号（去重排序）
- 预期范围自动合并为 `[[1,14]]`，`missing_ranges` 随之基于合并范围重新计算
- 帧 15 这种落在该胶卷**所有**预期范围之外的扫描帧，不计入缺帧，列入 `out_of_range_frames`

### 2. 查询批次

```bash
curl http://localhost:8000/batches/b-2026-001
```

### 3. 撤销误导入批次

```bash
curl -i -X DELETE http://localhost:8000/batches/b-2026-001
```

成功返回 `204 No Content`。服务在**同一个 SQLite 写事务**内完成删除与重建，要么全部生效、
要么整体回滚：

- 删除该批次，并按**剩余批次的原导入顺序**重建该胶卷的：
  - **预期范围**（由剩余各批的起止重新聚合）；
  - **帧归属**（共享帧不随首个批次丢失——原属被删批次、但后续批次也扫到的帧，
    归属自动转移到最早扫到它的剩余批次；仅被撤销批次持有的帧才真正移除）；
  - **各批新增帧与重复帧明细**（跨批重复按新的前缀关系重算；**批内重复予以保留**）。
- 撤销后胶卷查询（`GET /rolls`、`GET /rolls/{roll_no}`）、补扫认领与后续导入去重
  均按新状态实时计算；原本已扫、撤销后重新缺失的帧会重新出现在缺帧区间并可被认领。
- **最后一批撤销后该胶卷视为不存在**：其帧与预期范围清空，相关查询返回 `404`；
  该胶卷未释放的历史认领同时失效，**不会阻碍同编号胶卷重新导入后的缺帧领取**；
  重新导入内容与已删批次相同也允许（按新批次处理）。
- 批次不存在 → `404`（数据不变）。
- **兼容性保护（409）**：由 1.1 及更早版本创建的历史数据库中，旧批次只保存了去重后的
  帧集合，无法区分批内重复与跨批重复。若撤销后剩余批次中存在这种旧批次，服务返回
  `409 Conflict` 且**不改动任何数据**，以免重算出错误的重复明细；被删批次本身是旧批次、
  或撤销的是该胶卷最后一批时不受此限制。1.2 起新导入的批次都保存原始帧列表（含批内重复，
  保序），可任意撤销。

### 4. 查询胶卷完整状态

```bash
curl http://localhost:8000/rolls/R-001
```

返回合并后的预期范围、全部帧号、连续缺帧区间、范围外帧，以及每个批次的明细
（各批次的原始帧、新增帧、重复帧）。

### 5. 列出全部胶卷汇总

```bash
curl http://localhost:8000/rolls
```

### 6. 认领补扫任务

```bash
curl -X POST http://localhost:8000/rolls/R-001/rescan-claims \
  -H 'Content-Type: application/json' \
  -d '{
    "claimant": "alice",
    "max_frames": 3,
    "ttl_seconds": 3600
  }'
```

字段说明：

- `claimant`：领取人标识（必填，去首尾空格）
- `max_frames`：本次最多领取的帧数（**正整数**）
- `ttl_seconds`：认领有效秒数（**正整数**）；到期后任务自动失效，帧段重新可领

服务端先计算该胶卷当前的连续缺帧区间，**扣除所有未到期认领**已占用的帧段，
然后**按帧号升序**取第一个连续缺帧段、自其起始帧起截断为不超过 `max_frames`
的连续闭区间，原子落库（`BEGIN IMMEDIATE` 写事务 + SQLite 写锁，并发请求串行化，
领到的帧段互不交叠）。响应 `201 Created`：

```json
{
  "id": "92825c49b6f14f4d8058cdd50d13a82b",
  "roll_no": "R-001",
  "claimant": "alice",
  "frame_start": 4,
  "frame_end": 6,
  "frame_count": 3,
  "max_frames": 3,
  "ttl_seconds": 3600,
  "created_at": "2026-09-23T10:50:45.825Z",
  "expires_at": "2026-09-23T11:50:45.825Z",
  "remaining_missing_ranges": [[4, 6]]
}
```

- 胶卷不存在（尚未导入任何批次）→ `404`
- 当前没有可领取的缺帧（全部缺帧已被未到期任务占用，或胶卷已扫齐）→ `409`
- `max_frames` / `ttl_seconds` 不是正整数、`claimant` 为空 → `422`
- 认领区间只覆盖**缺帧**：区间内帧若之后被新批次扫到，不会再被任何人领取；
  `remaining_missing_ranges` 为该任务帧段中**目前仍缺失**的连续帧段（随补扫进度缩短）

接着另一人再领（缺帧原为 `[4,7]`、`[11,11]`）：领到 `[7,7]`；第三个人领到 `[11,11]`；
再领返回 `409`，直到有人释放任务或任务到期。

### 7. 列出未到期的补扫任务

```bash
curl http://localhost:8000/rolls/R-001/rescan-claims
```

返回该胶卷全部**未到期且未释放**的任务（按帧号升序），每项含领取人、认领闭区间
`frame_start`/`frame_end`、`frame_count`、创建与到期时间，以及该区间内仍缺失的
`remaining_missing_ranges`；胶卷不存在返回 `404`，无任务时返回 `[]`。

### 8. 释放补扫任务

```bash
curl -i -X DELETE http://localhost:8000/rescan-claims/92825c49b6f14f4d8058cdd50d13a82b
```

成功返回 `204 No Content`，占用的帧段立即重新可被领取；
任务不存在、**已释放**、已到期或**已结案**均返回 `404`（重复释放幂等地得到 404）。

### 9. 提交补扫完成回执

领取人补扫完成后，凭**认领 ID**提交回执，携带本次补扫的**批次号**与
**实际扫到的非空帧列表**（原始列表，至少 1 个，批内重复会被识别为重复帧）：

```bash
curl -X POST http://localhost:8000/rescan-claims/92825c49b6f14f4d8058cdd50d13a82b/receipts \
  -H 'Content-Type: application/json' \
  -d '{
    "batch_id": "rs-2026-001",
    "frames": [4]
  }'
```

服务端以**认领闭区间**作为该补扫批次的预期范围（与普通批次一样可在批次接口
查询、可撤销），并在**同一个 SQLite 写事务**内依次完成：导入补扫批次
（写入帧归属、聚合预期范围）→ 持久化回执 → 将认领置为**已结案**。任一步失败
整体回滚，**数据不变**。首次提交返回 `201 Created`：

```json
{
  "id": "5f1c0b7a2e6b4e9d8c3a1f0b2d4e6a8c",
  "claim_id": "92825c49b6f14f4d8058cdd50d13a82b",
  "roll_no": "R-001",
  "claimant": "alice",
  "frame_start": 4,
  "frame_end": 6,
  "batch_id": "rs-2026-001",
  "frames": [4],
  "added_frames": [4],
  "duplicates": [],
  "repeated": false,
  "remaining_missing_ranges": [[6, 6]],
  "created_at": "2026-09-23T12:10:03.417Z"
}
```

规则与异常：

- **只接受未到期、未释放、未结案的认领**：认领不存在 → `404`；
  已到期或已释放 → `409 Conflict`。
- 提交的每个帧号都必须**落在认领闭区间** `[frame_start, frame_end]` 内，
  且提交时**仍属于该胶卷缺帧**（未被其他批次扫到）；任一帧违规即整体
  `409 Conflict` 且**不导入任何帧、不落回执、不结案**。
- **部分补扫**：只提交实际扫到的帧即可。结案后该认领不再占用帧段，
  `remaining_missing_ranges` 给出帧段内仍缺的闭区间（如上例的 `[6,6]`），
  这些剩余缺帧**立即可被其他人重新认领**，无需等待到期。
- **重试幂等**：相同认领、相同 `batch_id`、相同原始帧列表的重复提交返回
  `200 OK` 与已存回执（`"repeated": true`），**不会重复导入批次**。
- 对同一认领提交**不同内容**（改 `batch_id` 或帧列表）、或对**已结案**认领
  再提交新回执，均为 `409 Conflict` 且数据不变；`batch_id` 已被其他回执
  占用同样 `409`。
- 补扫批次与普通批次共用 `GET /batches/{batch_id}`、
  `DELETE /batches/{batch_id}`：撤销补扫批次后对应帧重新成为缺帧；
  已存回执仍可凭原始参数幂等查询（返回落库时的明细快照），已结案的认领
  不会因此复活，让出的帧段可被正常认领。
- `frames` 为空、`batch_id` 为空白 → `422`。

### 10. 交付快照与差异对比

#### 10.1 拍摄交付快照

```bash
curl -X POST http://localhost:8000/rolls/R-001/snapshots
```

服务在**一致性读**（`BEGIN IMMEDIATE` 与并发写入串行化）中固化拍摄瞬间该胶卷的：
**预期覆盖闭区间**（合并后）、**实扫帧**（去重排序）与**缺帧闭区间**，
返回可长期查询的快照 ID（`201 Created`）：

```json
{
  "snapshot_id": "ca1f7600507e488d956d6cb5f58132c0",
  "roll_no": "R-001",
  "expected_ranges": [[1, 14]],
  "frames": [1, 2, 3, 5, 8, 9, 10, 11, 12, 13],
  "missing_ranges": [[4, 4], [6, 7], [14, 14]],
  "created_at": "2026-09-24T08:00:00.000Z"
}
```

- 胶卷不存在（尚未导入任何批次）→ `404`。
- 快照只新增、从不修改：此后的**批次导入、撤销、补扫认领与回执**都不会改变
  快照内容；快照与业务数据同在一个 SQLite 库（`roll_snapshots` 表），随 volume 保留。

#### 10.2 查询当前相对快照的差异

```bash
curl http://localhost:8000/rolls/R-001/snapshots/ca1f7600507e488d956d6cb5f58132c0/diff
```

对**预期覆盖、实扫帧、缺帧三个维度独立比较**，分别给出相对快照**新增**
（当前有、快照无）与**消失**（快照有、当前无）的**闭区间**（`200 OK`）：

```json
{
  "snapshot_id": "ca1f7600507e488d956d6cb5f58132c0",
  "roll_no": "R-001",
  "roll_exists": true,
  "snapshot_created_at": "2026-09-24T08:00:00.000Z",
  "compared_at": "2026-09-24T09:30:00.000Z",
  "expected": { "added": [[15, 20]], "removed": [] },
  "frames":   { "added": [[4, 4]], "removed": [[5, 5]] },
  "missing":  { "added": [[15, 20]], "removed": [[4, 4]] }
}
```

规则说明：

- **按区间做集合运算，不逐帧展开大范围**：实扫帧在比较前先压成连续闭区间，
  集合差为双指针线性扫描；即使预期范围跨度达二十亿帧，也只与区间数量相关。
- 差异在一次只读事务中计算，三个维度彼此对应于同一当前状态。
- **即使胶卷最后一批被撤销**（胶卷当前视为不存在），只要快照属于该胶卷编号，
  仍返回 `200`：`roll_exists` 为 `false`，当前状态按空集合处理，
  差异表现为“快照固化的内容全部消失”；同编号胶卷之后重新导入，
  差异继续按新内容计算（会同时出现新增与消失）。此时对该胶卷**新建**快照仍为 `404`。
- 未知快照 ID、或快照归属的胶卷编号与 URL 中的 `roll_no` 不匹配 → `404`。

### 11. 胶卷帧号扫描溯源

供档案员追查某胶卷区间内**每个实际存在的帧**分别由哪些批次扫描：

```bash
curl 'http://localhost:8000/rolls/R-001/frame-provenance?start=0&end=12&limit=3'
```

查询参数：

- `start` / `end`：帧号**闭区间**（非负整数，且 `end ≥ start`）
- `limit`：每页最多返回的帧数（**正整数**）
- `cursor`：可选游标，传**上一页响应中的 `next_cursor`**（即上一页末帧号）；
  续页只返回帧号严格更大的帧

只按**实际存在的帧号**升序分页（缺帧、从未扫到的帧号不占位），底层走
`roll_frames` 主键的键集分页（`frame_no > cursor`），**不逐帧遍历区间跨度**，
因此即使 `end` 给到二十亿，开销也只与命中帧数、`limit` 与该胶卷批次数有关。
响应 `200 OK`：

```json
{
  "roll_no": "R-001",
  "frames": [
    {
      "frame_no": 1,
      "first_scan_batch_id": "b-2026-001",
      "in_expected_coverage": true,
      "batches": [
        { "batch_id": "b-2026-001", "occurrence_count": 1 }
      ]
    },
    {
      "frame_no": 2,
      "first_scan_batch_id": "b-2026-001",
      "in_expected_coverage": true,
      "batches": [
        { "batch_id": "b-2026-001", "occurrence_count": 2 },
        { "batch_id": "b-2026-003", "occurrence_count": 3 }
      ]
    }
  ],
  "next_cursor": 2
}
```

逐帧字段：

- `first_scan_batch_id`：**最早有效批次**（该帧当前归属批次）。
  **撤销批次后按剩余批次实时重算**：若首扫批次被撤销、后续批次也扫到该帧，
  首扫归属随即转移给最早的剩余批次；仅被撤销批次持有的帧直接不再出现。
- `batches`：扫描过该帧的**全部有效批次，按批次原导入顺序**排列。
- `occurrence_count`：该帧在对应批次**原始帧列表**中的出现次数
  （批内重复如实计数）。由 1.1 及更早版本导入的**旧批次没有原始列表**，
  该值返回 `null`，**不推断重复次数**。
- `in_expected_coverage`：该帧是否位于胶卷**当前预期覆盖**
  （全部批次预期范围合并后的闭区间）内；撤销导致预期范围收缩时实时反映。

翻页规则：

- 用本页响应的 `next_cursor` 作为下一页的 `cursor`；无后续帧时 `next_cursor` 为 `null`
  （正好取满一页但后面无数据时同样为 `null`）。
- 游标是“上一页末帧号”，续页严格取帧号更大的帧；游标落后于 `start` 时
  会自动回退到 `start` 起（不会跳过 `start` 帧）；游标越过 `end` 时返回空页。
- 区间内没有任何实际帧时，`frames` 为空、`next_cursor` 为 `null`。

异常：

- 参数缺失/非整数、`start` 或 `end` 为负数、`limit` 不是正整数、`cursor` 为负、
  **`end < start`** → `422 Unprocessable Entity`
- 胶卷不存在（尚未导入任何批次，或最后一批已被撤销）→ `404 Not Found`

### 12. 健康检查

```bash
curl http://localhost:8000/health
```

## 业务规则

1. **跨批次合并**：同一 `roll_no` 的所有批次共享帧号集合与预期范围集合。
2. **重复帧**：同一批次内重复出现、或此前批次已扫到的帧号，只计一次，在
   `duplicates` 中单独列出（去重排序）。
3. **连续缺帧区间**：该胶卷所有批次的预期范围先做区间合并（重叠/相邻即合并），
   再扣除已扫帧，输出若干连续闭区间，如 `[4,4]`、`[6,7]`。
4. **幂等导入**：以 `(胶卷编号, 预期范围, 帧号集合)` 的 SHA-256 指纹判重，
   重复导入不改变结果。显式 `batch_id` 若被**不同内容**占用返回 `409`。
   新批次保存提交时的**原始帧列表**（含批内重复、保序），用于撤销时精确重建。
5. 帧号为非负整数；预期范围为闭区间。
6. **批次撤销**（`DELETE /batches/{batch_id}`）：
   - 删除与重建在同一 `BEGIN IMMEDIATE` 写事务中完成，任何一步失败整体回滚；
     批次不存在返回 `404`，成功返回 `204`。
   - 按剩余批次原导入顺序重建预期范围、帧归属与各批新增/重复明细：
     **共享帧不随首个批次丢失**（归属转移给最早含该帧的剩余批次），
     **批内重复保留**，跨批重复按新状态重算。
   - 最后一批撤销后胶卷视为不存在（查询返回 `404`，不出现在胶卷列表），
     其未结案、未释放的历史认领同时失效，不阻碍同编号胶卷重新导入后的领取；
     已提交回执的认领保持已结案（补扫批次随撤销被移除，需要时可重新认领）。
   - 撤销后缺帧区间、补扫认领与后续导入去重均以新状态为准。
   - 旧版库的历史批次缺少原始帧列表，若剩余批次含此类旧数据则返回 `409`
     且数据不变；服务启动时会幂等升级库表（新增 `raw_frames_json` 列），
     无需手工迁移。
7. **补扫任务认领**：
   - 可领帧 = 当前连续缺帧区间 **− 全部未到期、未释放认领** 占用的帧段；
     按帧号升序取首段，自起始帧截断为长度不超过 `max_frames` 的连续闭区间
     （不会跨越已扫帧，也不会与他人任务交叠）。
   - 分配在 `BEGIN IMMEDIATE` 写事务中完成，并发领取由 SQLite 写锁串行化，绝不交叠。
   - 新批次扫到的帧立即从缺帧中消失，任何任务（含已占用该帧的任务）都不会再持有它；
     任务响应中的 `remaining_missing_ranges` 实时反映其帧段内仍缺的部分。
   - 任务在 `expires_at` 到期后自动失效（查询与分配时即时判定，无需后台清理），
     帧段自动让出；主动 `DELETE` 则立即让出。重复释放、释放已到期/已结案/
     不存在的任务均为 `404`。
   - 胶卷不存在（尚未导入批次）时，认领与列表接口均返回 `404`；暂无可领帧返回 `409`。
   - 认领记录持久化在同一 SQLite 库（`rescan_claims` 表），随 volume 保留。
8. **补扫完成回执**（`POST /rescan-claims/{claim_id}/receipts`）：
   - 请求体为补扫批次号 `batch_id` 与实际扫到的非空帧列表 `frames`
     （原始列表，至少 1 个；批内重复识别为重复帧）。
   - 仅接受**未到期、未释放、未结案**的认领（不存在 `404`，到期/已释放 `409`）；
     帧号须全部落在认领闭区间内、且提交时仍属该胶卷缺帧，任一违规返回 `409`
     且数据不变。
   - 以**认领闭区间**作为补扫批次的预期范围；**批次导入、回执持久化、认领结案**
     在同一 `BEGIN IMMEDIATE` 写事务内完成，失败整体回滚。
   - **部分补扫**只导入实际扫到的帧；结案后认领不再占用帧段，剩余缺帧
     **立即可重新认领**（`remaining_missing_ranges` 实时反映仍缺部分）。
   - 相同认领 + 相同批次号 + 相同原始帧列表的重试返回已存回执
     （`200`，`"repeated": true`），不重复导入；内容变更或对已结案认领
     再提交新回执均为 `409`；回执与认领一一持久化在 `rescan_receipts` 表。
9. **交付快照与差异**（`POST /rolls/{roll_no}/snapshots`、
   `GET /rolls/{roll_no}/snapshots/{snapshot_id}/diff`）：
   - 创建时在一致性读中固化当时的**预期覆盖闭区间、实扫帧（去重集合）、
     缺帧闭区间**，持久化在 `roll_snapshots` 表（启动时幂等建表，旧库自动补建）；
     胶卷不存在返回 `404`。
   - 快照一经生成**只读**：批次导入、撤销或补扫均不修改快照内容，可长期凭
     快照 ID 查询；同一胶卷可拍摄任意多张快照。
   - 差异对比对预期覆盖、实扫帧、缺帧**三个维度独立做双向区间集合差**
     （`added` = 当前−快照，`removed` = 快照−当前）；实扫帧先压缩成连续闭区间，
     全程不逐帧展开大范围（集合差为有序区间的 O(n+m) 线性扫描）。
   - 胶卷最后一批被撤销后，归属该胶卷的快照仍可对比：返回 `200`、
     `roll_exists=false`，当前按空状态处理（快照内容全部计入 `removed`）；
     未知快照 ID 或胶卷编号与快照不匹配返回 `404`。
10. **胶卷帧号扫描溯源**（`GET /rolls/{roll_no}/frame-provenance`）：
    - 按实际存在的帧号升序**键集分页**：帧号闭区间 `start`/`end`（非负、end ≥ start）、
      正整数 `limit`、可选 `cursor`（上一页末帧号，续页严格取更大帧号）；
      查询走 `roll_frames` 主键（`frame_no > cursor AND frame_no <= end`），
      不逐帧遍历区间跨度；缺帧与未扫帧号不占页。
    - 每帧返回最早有效批次（首扫归属，即当前 `roll_frames` 归属）、按批次
      **原导入顺序**排列的参与批次，以及该帧在各批**原始列表中的出现次数**；
      旧批次缺少原始列表时次数为 `null`，不推断。
    - `in_expected_coverage` 按当前合并后的预期闭区间实时判断。
    - **撤销批次后实时重算**：归属按剩余批次原导入顺序重建，首扫归属随之转移，
      仅被撤销批次持有的帧不再出现；最后一批撤销后接口返回 `404`。
    - 参数无效（含 `end < start`、非正 `limit`、负数或非整数参数）返回 `422`。
